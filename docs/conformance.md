# Standards and acceptance evidence

This matrix defines the implemented profile and connects its obligations to executable evidence. It is an engineering self-assessment, not an independent conformance certification. Source `47b3543` passed a clean build with 169 unit and 174 PostgreSQL/HTTPS integration tests, zero failures/errors/skips and zero SpotBugs findings. Its [actual CI evidence](../qualification/evidence/correction-ci-final.json) also records source/JAR/container license delivery, both independent clients under the default configuration, explicit strict mode, all six packaged browser profiles, same-version/V9 recovery and separate Java/OS advisory checks. Additional local measurements and restoration records are in the maintained [qualification index](../qualification/evidence/README.md). Historical checkpoint records remain unchanged and do not qualify later source.

The current project license is Apache License 2.0. [Distribution review and actual artifact inspection](third-party-licenses.md) record the separate upstream licenses, resolved Spring Session metadata error and source/JAR/container notice obligations. License selection and an unrequested external certification are not completion blockers.

The primary RFCs, their verified errata and relevant update boundaries are recorded in [standards review](standards-review.md). The application owns the protocol responsibilities described in [ADR 0001](adr/0001-protocol-engine.md); Spring Security and iCal4j are not advertised as turnkey CalDAV engines.

## Synchronization, durability and permission changes

| RFC6578 obligation | Implementation/evidence |
| --- | --- |
| Initial state, incremental resources and deletions | `CalendarStore` allocates revisions under a per-collection row lock inside the mutation transaction, atomically storing content/indexes/revision/history. V10 immutable resource versions, normalized historical property rows and durable continuations freeze an upper revision across separate HTTP requests. Initial and incremental reports use consistent version/history snapshots without a database transaction held open between pages; see [ADR 0004](adr/0004-resumable-synchronization.md). `CalendarStoreIT.serializesCommitOrderWhileReportsUseCommittedSnapshots` explicitly exercises the late-commit sequence-number hazard. |
| Scoped tokens and invalid state | Stable tokens include collection identity, state generation and global recovery epoch. Opaque continuation state is additionally bound to the requesting account, fixed lower/upper revisions, cursor, retention floor and 24-hour expiry; every page rechecks account state and current collection authorization; sharing/group changes and restoration invalidate affected state. Invalid/wrong-collection/old-generation/retention-expired tokens fail with valid-sync-token. Revoked permissions cannot use old tokens to access content. |
| Limited results and interrupted responses | Initial and incremental pages honor the RFC 6578 truncated 207/collection-507/continuation-token contract. Valid positive client result ceilings above the server page cap are accepted and capped, including integers larger than a Java int. An explicit empty property selection still produces a successful empty propstat for each changed member. The cursor records the last delivered name at a frozen watermark; incomplete pages never append the latest live revision. Retry does not consume a token. Writes above the watermark, deletions, delete/recreate and names across cursor boundaries are delivered by the subsequent stable-token traversal. Metadata requests do not fetch bodies. Calendar-data pages additionally bound retained raw bodies and charge selected serialized XML, escaping, properties and construction work. A first item that cannot fit fails explicitly without a successful token; a truncated page must make progress. `SyncPagingIT` covers more than 10,000 resources and 32 MiB, small pages, metadata/content, concurrent mutations, retries, retention, revocation and restart. No separate pagination API or PROPFIND pagination is invented. |
| History retention | Change records, immutable resource bodies and property snapshots are retained indefinitely by default; protect historical private data in PostgreSQL backups. Transactional `CalendarStore.pruneHistory` minimum-token invalidation is tested; there is no automatic history-pruning job or exposed operator API. Expired continuation rows are independently reclaimed in bounded batches; expiry enforcement does not depend on that cleanup. Monitor growth as described in [operations](operations.md). |
| Restart/restore | Durable PostgreSQL state survives process restarts. Offline restore rotates recovery/account epochs, disables every account and clears restored factors/sessions/DAV/OAuth credentials before individually verified recovery; restoration also clears durable continuation rows while retaining authoritative version/property history, so old tokens and credentials cannot silently revive. Forward migrations V10–V13 preserve already-applied V1–V9 checksums. `SyncPagingIT` exercises V9 upgrade; the packaged operation and HTTPS restoration entry points cover the new schema and inherited property metadata. Prior local and real-provider HTTPS restoration passed old-token rejection, fresh synchronization, authoritative task bytes and separately recovered READ-recipient access/revocation; these are separate from database-only checks. |

## Declared profiles and exclusions

* **Digest deviation:** RFC4918 §20's historical Digest requirement is deliberately not implemented. The HTTPS Basic device-credential/Bearer profile avoids the weak password-storage requirements identified by [Spring's Digest guidance](https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/digest.html). Literal satisfaction of every historical DAV security requirement is not claimed.
* **Sync Depth compatibility:** RFC6578 §3.2 requires HTTP Depth 0. The executable JAR and Compose both default to the narrow Depth 1 accommodation only for DAV:sync-collection with XML sync-level 1. Missing Depth means zero and explicit Depth 0 remains supported. `BUSYSTACK_DAV_ALLOW_SYNC_DEPTH_ONE=false` is the strict override. Invalid/duplicate/infinite Depth still fails. Scope, ACLs, snapshots, tokens and limits are unchanged. This deliberately deviates from the nonzero-header rejection requirement. Current independent qualification leaves the setting absent and records actual effective protocol behavior separately from configuration input; a separate packaged HTTPS profile verifies explicit false.
* **Stored scheduling data:** RFC6638 scheduling, invitation/email delivery, push and server-executed reminders are outside scope and not advertised. Organizer/attendee/alarm preservation does not imply execution.
* **Other extensions:** DAV locking, extended MKCOL, proprietary client sharing, CardDAV and a general WebDAV file service are not advertised. Required calendar namespace operations remain implemented.
