# Standards and acceptance evidence

This matrix defines the implemented profile and connects its obligations to executable evidence. It is an engineering self-assessment, not an independent conformance certification. A test's presence does not establish that a particular artifact passed it. The final combined source build passed 149 unit and 134 integration tests with no skips and SpotBugs zero findings; packaged SQL, root/proxy/browser, real upstream login, local/federated HTTPS restoration and measured workload profiles also passed on the recorded final image; historical V7 account artifacts are explicitly identified in [qualification evidence](../qualification/evidence/README.md).

The primary RFCs, their verified errata and relevant update boundaries are recorded in [standards review](standards-review.md). The application owns the protocol responsibilities described in [ADR 0001](adr/0001-protocol-engine.md); Spring Security and iCal4j are not advertised as turnkey CalDAV engines.

## Synchronization, durability and permission changes

| RFC6578 obligation | Implementation/evidence |
| --- | --- |
| Initial state, incremental resources and deletions | `CalendarStore` allocates revisions under a per-collection row lock inside the mutation transaction, atomically storing content/indexes/revision/history. Initial and incremental reports use consistent data/history snapshots. `CalendarStoreIT.serializesCommitOrderWhileReportsUseCommittedSnapshots` explicitly exercises the late-commit sequence-number hazard. |
| Scoped tokens and invalid state | Tokens include collection identity, state generation and global recovery epoch; sharing/group changes and restoration invalidate affected state. Invalid/wrong-collection/old-generation/retention-expired tokens fail with valid-sync-token. Revoked permissions cannot use old tokens to access content. |
| Limited results and interrupted responses | The selected profile rejects an unsatisfied bounded result request with the defined limit error; it does not return an advancing token for omitted changes. Raw tests distinguish protocol limits, cardinality and malformed responses. No undocumented pagination cursor is invented. |
| History retention | Changes/deletion records are retained indefinitely by default. Transactional `CalendarStore.pruneHistory` minimum-token invalidation is tested; there is no automatic pruning job or exposed operator API. Monitor growth as described in [operations](operations.md). |
| Restart/restore | Durable PostgreSQL state survives process restarts. Offline restore rotates recovery/account epochs, disables every account and clears restored factors/sessions/DAV/OAuth credentials before individually verified recovery; old tokens and credentials cannot silently revive. Final local and real-provider HTTPS restoration passed old-token rejection, fresh synchronization, authoritative task bytes and separately recovered READ-recipient access/revocation; these are separate from database-only checks. |

## Declared profiles and exclusions

* **Digest deviation:** RFC4918 §20's historical Digest requirement is deliberately not implemented. The HTTPS Basic device-credential/Bearer profile avoids the weak password-storage requirements identified by [Spring's Digest guidance](https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/digest.html). Literal satisfaction of every historical DAV security requirement is not claimed.
* **Sync Depth compatibility:** RFC6578 §3.2 requires HTTP Depth 0. Strict default rejects other depths. Explicit `BUSYSTACK_DAV_ALLOW_SYNC_DEPTH_ONE=true` accepts Depth 1 only with XML sync-level1 for the tested python-caldav 3.6.0 and Thunderbird 157.0.1. Invalid/duplicate/infinite Depth still fails. Scope, ACLs, snapshots, tokens and limits are unchanged. These client sync results qualify this documented compatibility profile, not the strict baseline.
* **Stored scheduling data:** RFC6638 scheduling, invitation/email delivery, push and server-executed reminders are outside scope and not advertised. Organizer/attendee/alarm preservation does not imply execution.
* **Other extensions:** DAV locking, extended MKCOL, proprietary client sharing, CardDAV and a general WebDAV file service are not advertised. Required calendar namespace operations remain implemented.
