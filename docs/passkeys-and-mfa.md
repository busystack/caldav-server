# Passkeys and the MFA policy

BusyStack connects Spring Security 7.1.2's WebAuthn mechanisms and WebAuthn4j verification to PostgreSQL. Account configuration is available at `/security/passkeys`. The interface uses local JavaScript and has no CDN or analytics dependency. Event and task content is managed by CalDAV clients.

Sign in at `/login` using your account password. The first passkey enrollment requires a primary factor verified in the last ten minutes: a password for local users, or verified organization OIDC login for externally managed users. Enroll a resident passkey using an authenticator that supports user verification; BusyStack requires verification for registration and authentication. Then use **Verify passkey** to complete password plus WebAuthn MFA for the same account. Additional passkey enrollment and credential removal require the appropriate primary factor and WebAuthn within the same ten-minute period. See [optional Keycloak configuration](keycloak.md) for the externally managed policy.

Account mutations and client authorization require recent MFA. The account overview can be read with a single authenticated factor, so an account without a passkey can reach enrollment. These explicit rules do not claim that a password-only overview is MFA. Losing the password or all authenticators does not grant an HTTP recovery bypass.

The relying-party ID is the hostname of the validated public base URL; the allowed origin is its exact scheme, hostname and port. A reverse-proxy path is not part of an origin. Changing the public hostname can make existing authenticator registrations unusable. Deployment URLs must therefore be selected deliberately. Production uses HTTPS; explicitly enabled HTTP loopback development is separate configuration.

Both the user handle and credential records are persistent. A user handle maps to the internal account UUID, and lookup uses the account's current username. Renaming a login therefore does not change calendar ownership or replace the registered passkey handle. Spring's JDBC credential repository stores public keys, authenticator metadata, signature counters, labels, and usage timestamps. Passwords and private authenticator keys are never stored in passkey records.

The server serializes each session's registration/authentication ceremonies and consumes their challenges once. Challenges expire after five minutes on the server. Registration challenges remain associated with the authenticated session. Failed assertions consume their challenge and require requesting fresh options. PostgreSQL transactions serialize writes for a credential; credential ownership and public key are immutable, counters cannot regress, and deletion records prevent a previously read assertion from reinserting a removed credential. Session IDs rotate after successful password or passkey authentication. Account disabling is checked for existing browser sessions and during passkey authentication.

The local operator recovery command is documented in [operations](operations.md). It resets the selected account's password and revokes independently issued access, including registered passkeys. Use the documented offline procedure with a private password file. Recovery requires control of the server and database; there is no public first-run or recovery endpoint. Stop all application instances before this offline operation and restart afterward; this drops their in-memory browser sessions. Hot recovery does not currently track a per-account session epoch and must not be advertised as revoking already running sessions. Keep another administrator and more than one authenticator where appropriate.

Implementation evidence is in `PasskeyCeremonyGuardTest`, `PasskeyPersistenceIT`, and the separate Chromium virtual-authenticator qualification harness. Check the qualification record for actual executed results. Database round-trip tests do not establish cryptographic verification, and a virtual authenticator does not qualify every hardware or synced passkey provider.

The framework APIs and exact source inspected are [Spring Security passkeys](https://docs.spring.io/spring-security/reference/servlet/authentication/passkeys.html), [Spring Security MFA](https://docs.spring.io/spring-security/reference/servlet/authentication/mfa.html), and the [published WebAuthn 7.1.2 source artifact](https://repo.maven.apache.org/maven2/org/springframework/security/spring-security-webauthn/7.1.2/spring-security-webauthn-7.1.2-sources.jar). Notable application integration requirements are the enrollment filter's position before ordinary authorization rules, explicit enabled-account checks in the user lookup, persistent repositories, challenge lifetime enforcement, and session fixation protection. These controls still need independent security review; they are not a certification or equivalence claim.
