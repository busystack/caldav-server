# Calendar semantics and bounded work

Complete accepted UTF-8 resource bytes remain authoritative. Every TZID parameter must have a matching embedded VTIMEZONE, including built-in IANA identifiers, as required by RFC4791 section4.1; the server does not silently supply missing definitions. Ordinary GET and calendar-data without selectors serve those bytes. Derived iCal4j models are used for validation and queries. Report copies retain original lexical DURATION, RDATE PERIOD and TRIGGER values: P1D and PT24H have different meanings across a daylight-saving change. Partial projections preserve those distinctions and property parameters. Expanded reports are derived representations. Explicitly typed extension DATE-TIME/PERIOD values with TZID are converted to UTC while retaining extension parameters; an untyped timezone-qualified extension that cannot be interpreted fails explicitly. Expanded UTC date properties preserve extension parameters, and alarm trigger instances become equivalent absolute UTC values so nominal-day offsets and repeated alarms retain their original instants after timezone conversion.

Calendar-query uses typed component, property, parameter, text and time-range filters. The required `i;ascii-casemap` and `i;octet` collations are supported; unsupported collations fail explicitly. DATE, floating, UTC and TZID-qualified values remain distinct. Embedded VTIMEZONE definitions and report/collection floating-timezone settings are used without fetching external TZURL data. Component and enum names are case insensitive; TEXT matching follows its declared collation.

Recurrence generation uses iCal4j 4.4.0 RRULE operations, with application handling for RDATE/EXDATE, detached replacements and RANGE=THISANDFUTURE. Verified [RFC5545 erratum4271](https://www.rfc-editor.org/errata/eid4271) applies section3.3.5 to nonexistent local recurrence times: the pre-gap UTC offset determines their instant, and they consume COUNT. Invalid calendar dates remain omitted without consuming COUNT. Calendar durations apply nominal days before elapsed clock units; explicit DTEND/DUE retains exact elapsed duration. RFC 4791 section 9.9 task time-range rows, including undated, due-only, completed-only and created/completed tasks, have separate semantics from event overlap. Relative and repeated stored alarms are considered in query matching, including triggers outside the parent event interval; no alarm is executed. Free/busy excludes cancelled and transparent events, preserves tentative types and merges only equal busy types.

One query/projection/free-busy instance carries the cumulative budget for a REPORT across its resources. Defaults bound output to 10,000 instances, estimated candidate work to 500,000, RRULE increments to 900 and recurrence search spans to 3,660 days. RRULE candidate work is checked before library expansion; the increment bound is below the pinned library's internal 1,000-increment stopping threshold, so that threshold cannot silently produce a successful partial answer. COUNT rules are evaluated from their original anchor through bounded library windows: small expired series do not scan every intervening year, while genuinely large histories can exceed the work bound. Open-ended negative answers beyond the bounded horizon fail rather than omit possible future matches. Limits produce explicit protocol errors through the HTTP adapter. Expanded component and repeated-alarm copies reserve a conservative cumulative 16MiB report-size estimate before cloning; separate projection input/output limits also run before copying, preventing a large recurring property from multiplying into an unbounded in-memory report.

Input is limited to 1 MiB, with separate component/property/parameter/nesting bounds. Calendar text rejects disallowed C0 controls, DEL, isolated UTF-16 surrogates and U+FFFE/U+FFFF, so accepted resources can be represented in XML 1.0 calendar-data. TAB, folded lines, CRLF and valid Unicode remain accepted. This is a documented text security profile; it does not claim every possible UTF-8 noncharacter is accepted. Timezone observance recurrences are bounded before eager library zone construction. The narrow upstream builder patch documented in `ical4j-timezone-patch.md` preserves explicit future observance RDATE transitions and honors finite UNTIL/COUNT boundaries. Unbounded shapes Java annual transition rules cannot represent are materialized through at least now+3660 days; recomputed per-zone coverage metadata rejects temporal queries and expansion outside that horizon. Ordinary reads continue to preserve those resources.
