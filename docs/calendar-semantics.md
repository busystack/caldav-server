# Calendar semantics and bounded work

The [independent-audit correction record](standards-corrections.md) supersedes the earlier blanket validation claims. `CalendarConstraints` enforces component and cross-property requirements at the write boundary, and `RecurrenceRuleSyntax` checks original RRULE parts before library normalization can discard duplicates. No event series is expanded for write validation. The parsing input adapter unfolds octets before strict UTF-8 decoding, including folds inside a multibyte character, and canonicalizes only structural identifier spelling in a derived reader. Accepted authoritative octets, case-sensitive identifiers and values remain unchanged. These corrections do not modify the upstream-derived parser or timezone-builder sources.

`ObservanceZoneRules` constructs chronological rules from the submitted observances. Finite eras and explicit dates determine the final regime; an unbounded annual tail is admitted only after checking its ordering and offset continuity across the Gregorian cycle. Today's active STANDARD/DAYLIGHT pair is not used to select future rules. Unproven complex shapes retain explicit coverage limits and fail beyond coverage instead of returning guessed instants. List-TEXT filters use decoded values once, while URI and other non-TEXT properties retain their own representation.

Previously accepted invalid objects are not migrated, deleted, normalized or hidden. Owners can enumerate metadata with PROPFIND or metadata-only sync, retrieve exact bytes with GET, then conditionally replace the same UID using its ETag or delete it. New writes and transfers are checked before mutation. Reports encountering invalid legacy data fail explicitly rather than silently omit members; correct the reported objects through ordinary authorized operations. Keep a backup of the original bytes during remediation.

Non-Gregorian RSCALE execution remains unadvertised. An unsupported RSCALE is rejected with `CALDAV:supported-rscale`, following RFC 7529 §10's recommendation rather than accidentally executing a Gregorian interpretation. Legal leap-second `60` values remain a documented narrow limitation: the current temporal model rejects them instead of providing RFC 5545 §3.3.5's recommended `59` fallback. This is a SHOULD-level exception, not a claim of full leap-second support or a reason to rewrite stored bytes. The original leap-second/ordinary-second controls remain in the corpus and correction matrix.

Complete accepted UTF-8 resource bytes remain authoritative. Every TZID parameter must have a matching embedded VTIMEZONE, including built-in IANA identifiers, as required by RFC4791 section4.1; the server does not silently supply missing definitions. Ordinary GET serves those bytes. Calendar-data without selectors retains ordinary source spelling and folding; if folding splits a UTF-8 code point, the XML representation unfolds that sequence before decoding so semantic characters are preserved without replacement characters. It does not rewrite persistence or change the GET validator. Derived iCal4j models are used for validation and queries. Report copies retain original lexical DURATION, RDATE PERIOD and TRIGGER values: P1D and PT24H have different meanings across a daylight-saving change. Partial projections preserve those distinctions and property parameters. Expanded reports are derived representations. Explicitly typed extension DATE-TIME/PERIOD values with TZID are converted to UTC while retaining extension parameters; an untyped timezone-qualified extension that cannot be interpreted fails explicitly. Expanded UTC date properties preserve extension parameters, and alarm trigger instances become equivalent absolute UTC values so nominal-day offsets and repeated alarms retain their original instants after timezone conversion.

Calendar-query uses typed component, property, parameter, text and time-range filters. The required `i;ascii-casemap` and `i;octet` collations are supported; unsupported collations fail explicitly. DATE, floating, UTC and TZID-qualified values remain distinct. Embedded VTIMEZONE definitions and report/collection floating-timezone settings are used without fetching external TZURL data. Component and enum names are case insensitive; TEXT matching follows its declared collation.

Recurrence generation uses iCal4j 4.4.0 RRULE operations, with application handling for RDATE/EXDATE, detached replacements and RANGE=THISANDFUTURE. Verified [RFC5545 erratum4271](https://www.rfc-editor.org/errata/eid4271) applies section3.3.5 to nonexistent local recurrence times: the pre-gap UTC offset determines their instant, and they consume COUNT. Invalid calendar dates remain omitted without consuming COUNT. Calendar durations apply nominal days before elapsed clock units; explicit DTEND/DUE retains exact elapsed duration. RFC 4791 section 9.9 task time-range rows, including undated, due-only, completed-only and created/completed tasks, have separate semantics from event overlap. Relative and repeated stored alarms are considered in query matching, including triggers outside the parent event interval; no alarm is executed. Free/busy excludes cancelled and transparent events, preserves tentative types and merges only equal busy types.

One query/projection/free-busy instance carries the cumulative budget for a REPORT across its resources. Defaults bound output to 10,000 instances, estimated candidate work to 500,000, RRULE increments to 900 and recurrence search spans to 3,660 days. RRULE candidate work is checked before library expansion; the increment bound is below the pinned library's internal 1,000-increment stopping threshold, so that threshold cannot silently produce a successful partial answer. COUNT rules are evaluated from their original anchor through bounded library windows: small expired series do not scan every intervening year, while genuinely large histories can exceed the work bound. Open-ended negative answers beyond the bounded horizon fail rather than omit possible future matches. Limits produce explicit protocol errors through the HTTP adapter. Expanded component and repeated-alarm copies reserve a conservative cumulative 16MiB report-size estimate before cloning; separate projection input/output limits also run before copying, preventing a large recurring property from multiplying into an unbounded in-memory report.

Input is limited to 1 MiB, with separate component/property/parameter/nesting bounds. Calendar text rejects disallowed C0 controls, DEL, isolated UTF-16 surrogates and U+FFFE/U+FFFF, so accepted resources can be represented in XML 1.0 calendar-data. TAB, folded lines, CRLF and valid Unicode remain accepted. This is a documented text security profile; it does not claim every possible UTF-8 noncharacter is accepted. Timezone observance recurrences are bounded before application rule construction. The active `BoundedTimeZoneRegistry` implements the supported registry interface and uses its registry-local ZoneId pool; it does not invoke the historical upstream-derived timezone builder. `ObservanceZoneRules` preserves chronological explicit RDATE transitions and finite UNTIL/COUNT histories. Annual future coverage requires a proof of the eventual transition cycle. Unproven unbounded shapes receive a finite materialization horizon and explicit coverage metadata; temporal queries and expansion beyond proven coverage fail. Ordinary reads continue to preserve those resources. The older builder and its BSD attribution remain unchanged as historical provenance in `ical4j-timezone-patch.md`.
