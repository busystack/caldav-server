# iCal4j 4.4.0 timezone compatibility patch

The pinned `org.mnode.ical4j:ical4j:4.4.0` artifact has reproduced timezone-builder defects: explicit observance RDATE values after the current date are omitted, future UNTIL and COUNT boundaries become perpetual annual rules, and a valid annual rule without BYMONTH does not inherit DTSTART's month. Java ZoneRules annual lastRules also cannot express arbitrary unbounded recurrence shapes such as INTERVAL=2.

`Ical4jZoneRulesBuilder` retains the upstream recurrence and transition implementation in this application's namespace. The correction removes the upper RDATE clipping filter, accepts preflighted per-observance finite/horizon endpoints, excludes finite rules from perpetual annual lastRules, inherits missing annual months, and allows lastRules to be disabled when a timezone needs bounded materialization. RRULE dates are generated by iCal4j; this application does not implement recurrence generation.

`BoundedTimeZoneRegistry` checks counts, increments and candidate work before either builder executes, including future finite boundaries. It obtains COUNT endpoints through progressively larger bounded iCal4j windows, charging every window and requiring a complete COUNT before accepting an endpoint. It materializes intervening annual RRULE transitions through future explicit RDATEs, avoiding a missing-history gap before those RDATEs. Registered rules are replaced before calendar values use them. No timezone URL is fetched.

Perpetual annual rules are used only for conservatively recognized shapes: yearly interval1, at most one month, one ordinal weekday or one fixed month day, matching single clock fields, and no BYSETPOS/BYYEARDAY/BYWEEKNO expansion. Other valid unbounded shapes are materialized with iCal4j through at least now+3660 days (or five years after a future first onset). Their coverage boundary is carried in Parsed/FloatingTimezone, recomputed from persisted raw definitions on every parse, and checked before time queries, expanded responses and padded alarm searches. An out-of-coverage request returns LIMIT_EXCEEDED; it never receives a silently simplified annual rule or a successful partial answer. Ordinary byte reads and non-temporal report copies preserve resources beyond that horizon. Excessive materialization work fails under the separate documented work limits.
