# ADR 0004: bounded synchronization with immutable revision history

Status: accepted for the completion pass. The algorithm is specified before its implementation.

RFC 6578 sections 3.6 and 3.7 require a truncated 207 multistatus to include a 507 response for the request collection and a token representing exactly the partial state delivered. A final revision alone cannot describe an incomplete initial listing. Nor is keyset paging through mutable current resource rows sufficient: a resource can disappear or move past a traversal boundary while requests are separated in time.

The collection row continues to serialize mutation revision allocation through transaction commit. V10 adds immutable resource versions and tombstones indexed by collection, name, and revision. The migration backfills current resources; existing change history remains usable as the set of names changed since an old stable token. Database triggers capture every resource insert/revision update and every deletion change, including the existing COPY/MOVE/property paths. Historical content is never reconstructed from live resource rows. Historical dead properties are separate indexed rows keyed to the immutable version, not one aggregate XML/JSON value: names-only queries never fetch XML, and one selected property never decompresses unrelated values. The deferred COPY fill only populates an empty final current-version property snapshot; later mutations cannot rewrite an older snapshot.

A traversal freezes an upper revision watermark W in its first repeatable-read request. An initial traversal selects the latest nondeleted version of every name at or before W. An incremental traversal selects the latest version of each changed name in (after,W], including tombstones. Both traverse names in PostgreSQL's explicit C collation with a strict keyset boundary. Mutations above W cannot change the frozen traversal; the final stable token is W, so those mutations are returned by the next incremental traversal. Delete/recreate is represented by the latest version at W, and each member URL occurs once per traversal.

A truncated page returns an opaque durable random UUID continuation referencing its original lower revision, W, initial/incremental mode, and last accepted name. Continuations are immutable: retrying an earlier token cannot advance or consume it. Each lookup checks the current enabled account, collection authorization, generation and recovery epoch, actor binding, expiry, and history-retention boundary. Continuing after a restart uses the same PostgreSQL state. Continuations are not credentials and do not confer access.

Persisting the final cursor uses a short Spring `REQUIRES_NEW`, read-committed transaction. PostgreSQL foreign-key parent checks can otherwise reject an insert in the report's older repeatable-read snapshot after an ordinary concurrent collection revision update, even though the referenced key is unchanged. This was reproduced by the writer-during-page-construction regression; no uncertain transaction is blindly retried. The helper rechecks current enabled state, effective access, generation, recovery epoch, revision and retention floor, then inserts under short parent key-share locks. Calendar data remains read from the original watermark. An outer serialization/response failure can leave an unused cursor, which confers no access and expires normally. The existing four DAV-work slots and ten-connection pool leave room for four report connections plus four nested cursor writes; pool acquisition/transaction failures fail the request without a success token. Cursor persistence has its own ten-second transaction/statement deadline: waiting behind a locked parent cannot indefinitely consume the servlet and DAV-work slot. Expected query/transaction deadline failures return HTTP 503 with `Retry-After: 1`, without a sync token; no automatic transaction retry occurs. A real HTTP regression first reproduced the unbounded wait and now requires bounded failure, no persisted cursor, slot release, and a successful subsequent report after releasing the writer.

Metadata selection does not retrieve body columns and keyset candidates are fetched in batches of at most 128 rows. Content-bearing selection retrieves at most one individually bounded resource at a time. A separate 4 MiB retained-body work budget and 4 MiB metadata estimate prevent a small calendar-data projection from retaining arbitrarily many large unprojected resources. The protocol supplies a function measuring the serialized selected response for each item, including escaped XML, requested property overhead and member URL. A row is accepted only if it fits the page byte budget; reserved document/collection-truncation/token overhead is charged outside that budget. A first item that cannot fit fails explicitly without a successful token. A page either advances at least one member or is complete; no no-progress continuation is issued. Both the client-requested result count and server-selected response byte budget can truncate. A client `DAV:nresults` is a maximum, so a valid larger positive integer is capped at the server's 10,000-member page limit without integer overflow; it is not rejected merely for exceeding that ceiling. Zero still cannot produce a usable page and fails explicitly without a token. A changed member always carries a successful `DAV:propstat`, including an empty `DAV:prop` when no properties were selected.

Continuation state expires after 24 hours. Independent scheduled read-committed maintenance prunes at most 1,024 expired rows per minute with `FOR UPDATE SKIP LOCKED`; expiration checks do not depend on cleanup. Maintenance never deletes inside a repeatable-read report, avoiding a concurrent-cleanup serialization race. Historical versions follow the existing explicit history-pruning policy: keep the newest version at or before the retention floor for initial listing, plus all versions above it. Pruning invalidates any older continuation. Restoration clears continuation state and rotates the global recovery and account security epochs according to the existing fail-closed recovery policy. Historical calendar bodies are part of PostgreSQL backup and require the same privacy protection as current bodies. All application instances must stop during the V10 history backfill and upgrade; this is not a rolling migration contract.

The cost is retained historical body storage, rather than whole-collection heap allocation or a database snapshot held open across HTTP requests. There is no total collection quota introduced to avoid paging. Expired or pruned traversals receive DAV:valid-sync-token and must restart; excessive individual responses receive the existing explicit limit error. The standard depth-zero contract and the separately documented narrow default depth-one accommodation are unchanged by the cursor algorithm.

Primary reference: [RFC 6578](https://www.rfc-editor.org/rfc/rfc6578.html#section-3.6).

Regression establishment: the original `SyncPagingIT.initialSmallPageReturnsContinuationRatherThanRejectingAcceptedCollection` and `initialSyncExceedsFormerRowAndBodyThresholdsWithoutMissingSubsequentChanges` both failed with `StoreException.Kind.LIMIT` against an isolated exact `495989d` source archive before correction (2026-10-27). The expanded current suite additionally covers frozen initial/incremental views, retries, delete/recreate, Unicode, metadata and response-work limits, expiry/retention/access/recovery/disable invalidation, durable state, property history, COPY, and forward migration from V9.
