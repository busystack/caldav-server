# BusyStack CalDAV Server 0.0.1

This preparation finalizes version metadata and local artifacts for the initial release. It starts from the audited correction baseline `a919d6324f2e1eea75de63b76b89cb065e7530cf`. Creating a release tag, publishing a GitHub release, merging to `main` and publishing container images remain separate owner decisions.

## Installation and artifacts

Build from the exact prepared source revision using the [installation and operations instructions](../operations.md). The executable artifact is `target/caldav-server-0.0.1.jar`; the source-built container is locally tagged `busystack-caldav:0.0.1`. A registry pull or downloadable GitHub release is not assumed. Source revision, JAR/image identities, distributable archive checksums, installation screenshots and final CI results are recorded in the [release verification record](../../qualification/evidence/releases/0.0.1/verification.json).

The default arrangement is one application and PostgreSQL, with HTTPS terminated by an operator-configured reverse proxy. It has no default administrator password or public first-run setup endpoint. Bootstrap the first administrator offline with an owner-only password file, then use browser administration to provision ordinary users. Each user enrolls and verifies a passkey before issuing named DAV credentials or changing collections and access. The operations guide covers the complete first-use sequence, client setup, controlled updates and restoration.

Apache-2.0 remains the project license. The executable JAR and image retain the project license, required third-party notices and runtime CycloneDX SBOM. See the [license inventory](../third-party-licenses.md) and [pinned runtime versions](../versions.md). Final release preparation does not change dependencies or database migrations; the supported schema is V1–V13.

## Supported functionality

* Independent CalDAV event (`VEVENT`) and task (`VTODO`) collections, discovery, queries, multiget and free/busy.
* Authoritative accepted iCalendar bytes, recurrence and exceptions, embedded custom time zones, conditional writes and ETags.
* Persistent incremental synchronization, bounded resumable pages, deletion history and restart recovery.
* Owner-controlled individual/group READ or WRITE sharing and DAV-visible access control.
* Local accounts, browser administration, persistent passkeys/MFA, recovery codes, revocable expiring DAV credentials and registered native OAuth clients using Authorization Code/S256 PKCE.
* Optional external OpenID Connect login through an existing Keycloak provider, with local account permissions and a local passkey factor.

The [standards correction submission](../standards-corrections.md) preserves the original 17 audit finding groups, their corrections and the later IV-CAL-01/IV-AUTH-01 follow-up. Those fixes include chronological custom-timezone interpretation, atomic write validation before normalization, legal structural case variations, semantic text matching, generated free/busy validity, WebAuthn account/state binding, accurate advertisements, XML extensibility, DAV properties, privileges and error contracts. Release preparation retains those implementations and original evidence. It is a developer verification submission, not independent auditor approval or certification.

## Compatibility and limitations

* **Thunderbird 157.0.1 default-timezone event creation failed in the observed desktop profile.** With **Use system timezone** selecting `America/Vancouver` (2026b data), the original graphical event contained six non-UTC `UNTIL` values in `STANDARD`/`DAYLIGHT` rules. The server correctly returned `403 CALDAV:valid-calendar-data` without creating the resource, consistent with [RFC 5545 §3.3.10](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.3.10). An undated task succeeded. Earlier controlled UTC/date-only/floating native-provider tests do not qualify this ordinary desktop timezone case. The release verification record preserves the original payload and failure; other zones/client versions remain unverified.
* **A bounded explicit UTC client profile passed.** In Thunderbird 157.0.1, select **Settings → Calendar → Set timezone manually → Etc/UTC** before creating events. Automated interaction with the headed client's real controls passed setup/discovery, event/task creation and editing, task completion, synchronization and confirmed deletion. Independent reads and PostgreSQL/application restart verified identical authoritative bytes/ETags; the same private Thunderbird profile restarted with its saved credential. The earlier accepted task and original rejected event fixture remain preserved separately. See [client setup](../operations.md#client-access-and-sync-compatibility) for instructions and the release record for screenshots and exact outcomes. This does not qualify other zones or physical authenticators, or claim manual human testing.
* Use HTTPS and a separate named DAV credential as the client's password; the primary account password does not authenticate DAV. Registered OAuth-capable clients can instead use the documented browser authorization flow.
* The default intentionally accepts `Depth: 1` only for sync-collection with XML sync-level 1 for the tested clients. Standard missing/`Depth: 0` behavior remains available. `BUSYSTACK_DAV_ALLOW_SYNC_DEPTH_ONE=false` selects strict depth handling. This is a documented RFC 6578 compatibility deviation, not a universal interoperability claim.
* The account interface manages collections, access and security; it is not a web calendar/task editor. Scheduling, invitation or notification delivery, alarm execution, CardDAV, general-purpose file hosting, DAV locking and non-Gregorian recurrence execution are outside the supported profile.
* Valid but computationally unsupported timezone/recurrence evaluations fail explicitly at their documented bounds. Leap-second values retain the documented rejection rather than the recommended ordinary-second fallback. Existing invalid legacy objects are preserved for authorized retrieval and repair; reports do not silently skip them. See [calendar semantics](../calendar-semantics.md).
* Synchronization/resource history is retained indefinitely by default and needs storage planning. Query/response limits are correctness controls, not a measured production capacity guarantee. The deployment does not provide automatic failover or high availability.
* Restoring an older database deliberately disables accounts and invalidates old sessions, factors, DAV/OAuth credentials and synchronization tokens before individual verified recovery. Backups and deployment secrets require private storage. Follow the supplied restore procedure; rolling back an application artifact does not roll back a database schema.
* Optional upstream account disabling/logout is not immediate push revocation of independently issued BusyStack access. The documented external-authentication freshness bound and local revocation policy apply; see [OIDC operations](../keycloak.md).
* Qualification is scoped to its recorded browser/client/runtime versions. Physical authenticators, other clients/platforms and operator-specific public DNS/certificates/network deployment are not established by virtual-authenticator or isolated test-CA results. The release record explicitly distinguishes automated browser/native-client tests from manual checks that could not be performed.
