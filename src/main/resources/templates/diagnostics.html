Troubleshooting

Database or startup failure

Check local readiness probes, database availability, configured credentials and migration validation in operator logs. A database outage can prevent authenticated administration itself; use deployment monitoring. Configuration is validated at startup. Keep database access private and use the documented backup and recovery procedure.

Organization identity provider unavailable

Check the explicitly configured issuer, provider availability, trusted TLS certificate and redirect URI. Discovery is deferred to organization sign-in. Local accounts work independently. Externally managed accounts fail closed when provider authentication is required, without a password fallback. Previously issued client access keeps only its existing freshness bound.

Authentication or permission failure

Ask the user to check credential expiration, revocation and recent primary/passkey verification. Review recorded security outcomes in the audit viewer. Local disabling denies access even if group memberships remain. Administration does not bypass collection ownership.

CalDAV compatibility and synchronization

Use the project's qualified client/version profile. The documented default supports narrowly bounded sync Depth: 1 and local timezone-observance UNTIL repair. Strict-mode settings are controlled by the operator. Permission or group changes can invalidate synchronization tokens; a client must start fresh synchronization.

Use the response's X-Request-ID to correlate safe request metadata with operator logs. Request contents and credentials must not be collected for troubleshooting. Backups and public TLS renewal are external operator responsibilities; their status is unknown here.
